# WEEKENDOG cleanup review v1

This Stage 2 review strengthens the evidence behind the ten manual-review groups from `cleanup-manifest-v1.md`. It authorizes no product-source deletion, database change, RPC grant change, remote migration, Vercel change, or evidence rotation.

## Method and evidence limits

- Repeated repository-wide caller searches across `app/`, `components/`, `lib/`, `scripts/`, `tests/`, `supabase/`, `types/`, `docs/`, and `package.json`.
- Treated App Router files, public RPC signatures, migrations, operational scripts, dynamically addressed assets, and user-owned untracked paths as externally discoverable surfaces even when static imports are absent.
- Used the Stage 1 connected Supabase advisor and plan observations as historical evidence only. No remote query, migration, grant, index, or data mutation was performed in Stage 2.
- Vercel/Preview access logs and current Supabase statement logs were not available through an authorized read-only project connection in this task. Their absence prevents deletion proof; it is not evidence of zero callers.
- The working tree was already modified and untracked before Stage 2. Pre-existing files remain user-owned.

## Decision vocabulary

- `retain`: an active caller, compatibility role, test, operational role, or provenance requirement is present.
- `deprecation_candidate`: no current in-repository product caller was found, but external/public use must be disproved before removal.
- `remote_review_required`: the candidate is a deployed database surface and requires representative telemetry plus separate remote approval.
- `product_decision_required`: ownership, compatibility, licensing, or user intent cannot be inferred from code.
- `proven_safe_but_not_deleted`: conclusive deletion proof exists, but this stage intentionally retained the item.

No candidate reached `proven_safe_but_not_deleted` in this review.

## Remote-change proposal, deliberately not applied

If later telemetry proves the two legacy public RPCs unused, the safe shape is a new forward-only migration that revokes only the exact approved signatures from `anon` and `authenticated`, paired with a separate reversal migration that restores the exact previous grants. Function bodies, V2/location grants, RLS, schemas, data, and historical migrations remain untouched. The same forward/reversal rule applies independently to any index decision after representative plan evidence.

No SQL draft was created in Stage 2 because telemetry and remote approval are still missing. Creating executable removal SQL now would imply confidence the evidence does not support.
